## 1. [P1] 点击设置导致界面异常

位置：`src/geochem_rag/app.py:243–249`。

`st.selectbox(..., key="retrieval_mode")` 创建后，又通过 `st.session_state.retrieval_mode = ...` 写入同一键。Streamlit 禁止同轮创建控件后写同名控件状态，slider/toggle 也使用相同模式。

复现：自建语料 + 假 provider 下运行实际 `main()`，初始页面无异常；点击“设置”得到：

```text
st.session_state.retrieval_mode cannot be modified after the widget with key retrieval_mode is instantiated.
```

修复：直接由带 key 的 widget 管理控件状态；需要持久保存的配置使用不同于 widget key 的字段，在初始化或回调中维护。关闭再打开设置不得丢失用户选择，切换面板不得重调 LLM。

验收：真实运行设置点击，切换检索方式、top-k、背景开关，关闭/打开面板，再提交问题核对参数仍生效。

## 2. [P1] 对话 API 出错后聊天页面崩溃

位置：`src/geochem_rag/app.py:272–278`、`:326–327`。

`_run_answer` 对 `Answer(status="error")` 保存 `kind="error"`、`answer` 和 `evidence`，没有 `text`。历史渲染统一按 `kind == "error"` 访问 `message["text"]`。检索失败路径有 text，对话失败路径没有，结构不一致。

复现：假对话 provider 抛出 `ProviderError("timeout", ...)`；实际 answerer 返回 error，rerun 之后历史渲染出现 `KeyError: 'text'`。

修复：统一 assistant 消息结构，或将持有 Answer 的错误消息交给 `_render_answer` 渲染；正常显示明确错误和重试方式，保留问题与历史。不要改成模板回答。

验收：检索超时、对话超时、鉴权失败、模型格式错误均不崩溃；问题仍可继续提交。

## 3. [P1] 索引就绪检查不检查覆盖，启动可能偷偷补全全库

位置：`scripts/run_streamlit_online.py:98–116`、`src/geochem_rag/app.py:126–145`、`src/geochem_rag/retrieval.py:323–349`。

启动器和应用只核对缓存 model。有效语料存在，但缓存为 `{"model":"BAAI/bge-m3","entries":{}}` 时，`check_prerequisites` 返回空错误列表，即“通过”。现有 `test_prerequisites_pass_when_ready` 甚至将这种空缓存列为成功样例。

随后 `Retriever.from_store` 会经 `EmbeddingCache.vectors_for` 自动向在线 provider 补齐缺失块。这违背“索引不完整给准备命令，不在启动时无提示重建全库”的要求，会使初次双击产生长时间等待及未说明的 API 调用。

修复：共同校验有效块 ID、文本 hash、覆盖率、向量维度/有限值和实际配置模型；缺失时阻止正常问答并给出对应 store/cache 的准备命令。启动验证必须只读，不隐式补齐；补齐放显式索引命令并显示进度。遵守 `GEOCHEM_EMBEDDING_CACHE` 等配置，启动器与应用不要各自硬编码不同解析逻辑。

验收：空 entries、缺一块、文本过期、错误维度、乱码缓存均提示未就绪且零嵌入调用；完整有效缓存正常启动。

## 4. [P2] 端口复用可能打开其他应用

位置：`scripts/run_streamlit_online.py:119–125`、`:160–166`。

`_http_ready` 只检查 localhost 响应码小于 500，无法判断是否属于本项目；本机其他 HTTP 服务返回 200 时也会被打印为“服务已经运行”并打开。

复现：模拟任意已响应的 HTTP 服务，main 返回 0，浏览器被打开，没有校验项目身份。

修复：用可核查的本项目实例信息（例如工作目录、进程/启动记录与服务状态联合检查）确认后再复用；其他应用占用端口时选择空闲端口或明确报冲突，不结束其他进程、不误开其他页面。服务就绪等待超时应可见。

验收：本项目运行时重复双击复用；其他 HTTP 服务和非 HTTP 进程占用时不误判；实际打开地址与使用端口一致。

## 5. [P2] 批量续跑绕过分块指纹，改参数不生效

位置：`scripts/import_all_pdfs.py:77–105`。

`process_one` 只要 import_state 中 SHA 的状态为 imported，就提前返回 resumed；没有比较本次 `max_chars`/规则指纹，因此从旧配置变成新配置时根本到不了带指纹的 `store.import_document`。store 单元测试通过不代表实际批量脚本生效。

复现：构造已导入记录，再以 `max_chars=900` 调用 `process_one`；结果 `resumed=True` 且 `ingest_pdf` 调用次数为零。

修复：state 同步保存指纹；仅在当前指纹、对应 store 的来源和块均一致时续跑跳过，缺指纹或变化时重新处理。修复 `rechunked` 状态的统计/报告，不能要求用户每次手工删除 state。重建时保留旧库快照或新库验证后切换，避免旧聊天引用指向改变后的同名块。

验收：实际批量流程从旧参数切到新参数生效；同配置续跑不重复；旧状态无指纹能迁移；导入中断后可续跑。
